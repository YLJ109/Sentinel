## 三、核心创新点

### 创新点 1：欺凌 / 打架 / 嬉闹 三分类判别

**要解决的问题**：所有同类系统共同的技术死穴 —— **欺凌与嬉闹无法区分**。
公开报道中，深圳某校团队自述「一开始的版本误报率非常高，有时候两个同学并肩走路，
系统也会发出警报」（[中国教育报](http://m.toutiao.com/group/7621148988997173810/)）。

**我们的方法**：现有方案普遍只判「距离近 + 手部动作快」，这三类场景在该维度上无法区分。
真正的差别在于**力量与主动权是否对等**。我们提出「互动对称性分析」，用四个可解释指标刻画：

| 指标 | 物理含义 | 欺凌场景表现 |
|---|---|---|
| 运动强度不对称 `asymmetry` | 两人手腕速度的相对差 | 一方猛烈挥臂、另一方几乎不动 |
| 退缩不对称 `retreat` | 两人「往后撤」倾向的差距 | 一方持续逼近、另一方持续后撤 |
| 追逃模式 `chase` | 是否存在明确的追者/逃者分工 | 单向追逐 |
| 压制姿态 `suppression` | 贴近时一方头部是否低于另一方肩线 | 一方被压制 |

加权累加为 `bully_score`，超过阈值判为**欺凌**，否则判为**打架**（对等冲突）；
四项同时「对等且无退缩且动作不剧烈」则判为**嬉闹**，不产生报警。

**技术要点（可复现）**：
- 逼近/远离速度**投影到两人连线方向**，因此"横向走过"不会被误判成逼近或逃离；
- 用「手腕**相对**身体中心」的速度而非绝对速度判断手势 —— 后者会把走路时的整体平移算成手势
  （此坑已实测复现并修复）；
- 归一化基准取 0.25 帧宽/秒（≈快走速度），依据是正常步行约 0.1、快走约 0.2、奔跑约 0.4 帧宽/秒；
- 指数滑动平均抑制单帧姿态抖动。

**验证**：`backend/scripts/check_bullying.py` 用五个合成场景逐帧验证，当前结果：

```
① 单向欺凌   → 欺凌 (bullying)  置信度 0.97   bully_score=0.551
② 对等互殴   → 打架 (fight)     置信度 0.95   bully_score=0.000
③ 课间嬉闹   → 未报警                          ← 误报被抑制
④ 并肩同行   → 未报警                          ← 误报被抑制
⑤ 排队贴近   → 未报警                          ← 误报被抑制
```

**诚实声明**：以上为合成场景，只验证**判别逻辑**。真实误报率/漏报率必须在校园实拍片段上统计。

### 创新点 2：多模态证据融合

视觉与语音在时间窗内互相印证时，报警置信度上浮、级别只升不降。
单一模态的误报（视觉误判、语音幻听）会被另一模态证伪。

**工程细节**：融合窗口取 **12 秒**是经过推算的 —— 语音是成句后才转写出来的，
从说话到出结果通常有 2~5 秒延迟，窗口定得过小（如 3 秒）会让互证几乎永远命中不了，
功能等于失效。这一取值依据写在代码注释中，答辩时可直接解释。

---

### 创新点 3：从「事件检测」到「风险预测」

`GET /api/risk/forecast` 输出点位风险画像：

- **风险分** = Σ(行为类型权重 × 指数时间衰减)，14 天半衰期，越久远的事件贡献越小；
- **高发时段**：按小时统计，指出某点位的高发时间；
- **趋势**：对比前后半程，样本少于 3 条时不判定趋势（避免用一两条事件就宣称「上升」）。

**学术对标**：公开数据集 NWPU Campus（西工大，CVPR 2023）同时提供「异常检测」与
「异常预测」两个 benchmark（[campusvad.github.io](https://campusvad.github.io/)），
说明「预测」是学界公认的下一步方向。

---

### 创新点 4：复核闭环与阈值自省

`GET /api/alarms/review/summary` 打通
**「报警 → 人工复核 → 误报统计 → 阈值调整 → 再训练」**：

- 按事件类型统计确认率；
- **把统计结论直接映射到可调参数名**（如 `BULLY_SCORE_THRESHOLD`、`ARGUE_MIN_FRAMES`）——
  否则「误报率高」只是一句结论，使用者不知道该改什么；
- 搭配 `scripts/export_samples.py`，把复核结论导成正/负样本，形成数据闭环。

**为什么这是答辩必答项**：评审一定会问「你怎么知道系统准不准」。
没有复核闭环，这个问题只能靠形容词回答。

---

### 创新点 5：隐私友好的数据最小化

- **隐私遮蔽区域**：目标落在遮蔽区内的不产生事件、不落任何取证；
- **取证留存期限**：默认 90 天自动清理；
- **仅做人脸定位、不做人脸识别**：合规风险显著低于身份识别类方案。

**关于端侧推理的取舍（答辩预设问题）**：曾评估「浏览器端提取骨架、画面不出本地」方案，
该路线需前端引入 ONNX Runtime（约 3MB wasm）与约 12MB 姿态模型，显著增加体积与客户端 CPU 占用；
而校园摄像头画面本就要接入学校既有监控平台，「画面不出浏览器」的实际增益有限。
因此选择服务端数据最小化，成本更低、效果更实在。

### 4.2 必须遵守的学术规范

1. **公开基准上必须说明划分方式** —— 若在 RWF-2000 上拿不到官方划分，

2. **跨库性能会掉点** —— 文献实测跨数据集 AUC 掉 20~30%

3. **数据集许可证需核对** —— RWF-2000 非商业且禁止再分发；NWPU Campus 仅限学术非商业。
   答辩演示可用，商用需另行授权。

### 4.3 建议的对照组设置

- A 组：仅几何规则（基线）
- B 组：规则 + 互动对称性分析
- C 组：B + 多模态融合

### 4.4 演示性评测：3 段真实素材

> **这一节是什么**：证明「链路在真实校园霸凌画面上确实跑得通、关键行为确实能检出来」的**演示案例**。
>
> **这一节不是什么**：**不是准确率指标**。素材只有 3 段、合计 33.2 秒，且是从真实视频里挑选的
> **高发片段**（不是连续监控录像），其中每一秒都含有事件。用它算出来的"召回率"会接近 100%，
> 而误报率**根本无法计算** —— 因为分母里没有"什么都没发生的时间"。
> 任何引用本节数字的地方都**不得**表述为准确率、精确率或召回率。

素材：`backend/data/eval/v1.mp4`（8.04s / 1280×720）、`v2.mp4`（15.08s / 1344×768）、
`v3.mp4`（10.04s / 1920×1080），均为 24fps，含求救、打人、踢人、言语施压、抽烟等行为。

按**帧节奏**分别回放两遍。之所以要测两遍：行为判定用的是**按帧计数的投票**
（`FIGHT_MIN_FRAMES`、`GROUP_BULLY_EDGE_FRAMES`、`EVENT_VOTE_WINDOW`），
帧间隔一变，"几次命中才算数"对应的真实时长就变了。表格里
`adaptive` 是视频文件分析（`video_pipeline` 的运动自适应采样），
`realtime` 是浏览器实时的节奏（`INFER_FPS_LIMIT` 限频 + 运动门控）。

| 视频 | 行为 | adaptive（离线） | realtime（实时节奏） |
|---|---|---|---|
| v1 | 打架 | 1 段，5.08–5.42s | **1 段，5.08–5.42s（完全一致）** |
| v2 | 打架 | 5 段 | 2 段 |
| v2 | 群体欺凌 | 16 帧 / 2 段 | 6 帧 / 3 段 |
| v3 | 打架 | 4 段 | 4 段 |
| v3 | 群体欺凌 | 34 帧 / 3 段 | 18 帧 / 1 段（6.04–8.12s，conf 0.96，4 人，内聚度 0.0） |

- **判定帧数合计**（同一事件会连续多帧上报，此列只反映采样密度，不是事件数）：
  adaptive `argue×947 / bullying×51 / crowd×353 / fall×42 / fight×46`；
  realtime `argue×381 / bullying×24 / crowd×219 / fall×41 / fight×19`。
- **语音**（ffmpeg 抽轨 + ASR + 三档关键词）：9 段转写，**8 段命中**。
  命中的关键片段包括「把钱拿出来」「老师，救救我，别逼我了，别喊人」「求求你们停下来」
  「不要这样放过我吧…我让你带的钱带了没？」「我要杀死你」。

**可以得出的结论（仅此三条）**：
1. 视觉与语音两条链路在真实霸凌画面上都能触发，群体欺凌（星型图判据）能够识别；
2. 实时节奏下结论与离线一致 —— **没有出现"离线能测、实时测不出"的能力倒退**，
   差异只体现在采样更稀导致的段数减少（v1 完全一致，v3 打架段数相同）；
3. 语音关键词对**明确的求助与勒索表达**命中率高，对**无关键词的威胁语气**会漏。

**必须如实写明的局限**：

| # | 局限 | 具体表现 |
|---|---|---|
| 1 | 样本量不足 | 3 段 / 33.2 秒 / 全为高发片段，**无法给出误报率与阈值敏感性** |
| 2 | 聚集误报 | 4 人即判聚集，教室里是常态；v3 仅 10 秒就产生 118 帧聚集记录，会淹没真正的欺凌事件 |
| 3 | 缺少事件段化 | 一次围殴会生成 6 条独立记录，没有"起止时间"语义，值班老师看到的是一串碎片 |
| 4 | 报警理由未可读化 | 判决依据是 `dist_ratio=0.16` 这类原始数值，非技术值班人员读不懂 |
| 5 | 语音存在语义盲区 | 「别这样，快点，不然对你不客气」这类**威胁语气但无词表关键词**的句子漏报；这属于语义理解层，不应靠继续扩词表解决 |
| 6 | 疑似跌倒未复核 | v1 报出 1 次跌倒，需人工目视确认是真阳性还是弯腰动作误判 |
| 7 | 阈值为小样本标定 | 所有阈值都是在这 3 段素材上人工调的，泛化性未经检验 |

### 4.5 性能基准（实测）

测试机：RTX 3060 Laptop（6GB），YOLOv8-Pose `IMGSZ=640` + FP16，
`ENABLE_FACE` / `ENABLE_FACE_ID` 全开。指标取 **p95** 而非均值：
均值会被偶发的快帧拉低，而实时链路的瓶颈恰恰出现在最慢的那几帧上。

**单帧端到端延迟（含检测 → 跟踪 → 行为判定 → 人脸检测/识别 → 情绪）**

| 输入尺寸 | 单帧 p95 | 等效帧率 | 对前端 10fps 送检的余量 |
|---|---|---|---|
| 640×360（浏览器实时送检） | 75.8 ms | 13.2 fps | **1.3× ✅** |
| 1280×720 | 199.5 ms | 5.0 fps | 0.5× ❌ |
| 1920×1080 | 396.2 ms | 2.5 fps | 0.3× ❌ |

**耗时归因（1920×1080）**

| 环节 | p95 |
|---|---|
| 姿态模型（YOLOv8-Pose） | 36.8 ms |
| **人脸检测（YuNet）** | **413 ms** |
| 完整链路 | 417.7 ms |

**瓶颈定位**：人脸检测占了 92% 的单帧成本，且它是**按整帧尺寸创建输入**
（`cv2.FaceDetectorYN.create(..., (w, h))`）—— 一个 230KB、设计给约 320×320 的模型，
在 1080p 上跑了 2.07M 像素。实测成本与输入面积近似线性：

| YuNet 输入 | 耗时 | 检出人脸 |
|---|---|---|
| 1920×1080 | 245 ms | 5 |
| 1280×720 | 101 ms | 5 |
| 640×640 | 52 ms | 4 |
| 320×320 | 10.5 ms | 3 |

**离线视频吞吐**：33.2s 视频用 109.7s 跑完，**处理/视频 = 3.31×**
（按此比例，10 分钟监控录像约需 33 分钟）。实时节奏回放时为 2.42×。

**可部署结论**：
1. **实时链路按设计可用**：前端固定按 640 宽送检（`RealtimeView.vue`，10fps），
   单帧 75.8ms 对应 13.2fps，余量 1.3×。这个余量同时说明
   **单卡只能稳定承载 1 路**，多路部署必须靠"送检前降采样"或增加算力；
2. **不要把原始分辨率直接送进模型**：这是 5 倍的成本差异，也是"实时链路与离线链路
   帧率语义必须分开验证"的根本原因；
3. **离线分析慢于实时是可接受的**（它是排队任务，不是在线服务），
   但若要"近实时回看"（如 5 分钟内出结果），需要先解决 YuNet 的输入尺寸问题；
4. 释放该瓶颈的改动方向已明确：把 YuNet 输入尺寸与帧尺寸解耦（加上限），
   实测可选 640×640（1080p 单帧约 396ms → 约 130ms），**代价是小脸召回下降（5 张 → 4 张）**。
   该改动会改变检测结果，因此**不与回归验证混在同一次改动里**，单独评估。

**判别逻辑回归（合成场景，`scripts/check_bullying.py`）**

| 场景 | 期望 | 实测 |
|---|---|---|
| 单向欺凌（A 逼近挥臂、B 后撤低头） | 欺凌 | ✅ 欺凌，conf 0.97 |
| 对等互殴（相向逼近、双方猛烈挥臂） | 打架 | ✅ 打架，conf 0.95 |
| 课间嬉闹（贴近、轻微推搡、幅度对等） | 不报警 | ✅ 未报警 |
| 并肩同行（同速同向、无动作） | 不报警 | ✅ 未报警 |
| 排队贴近（位置固定、无动作） | 不报警 | ✅ 未报警 |

⚠️ 合成数据只能验证**判别逻辑本身**，不能替代真实场景的误报率／漏报率统计。

### 4.6 补充采集方案（下一阶段）

第 4.4 节的七条局限里，前六条都指向同一个前提：**先把数据补上**。以下是可执行的采集与标注方案。

**一、拍什么 —— 按「场景 × 行为 × 人数」分层，正负样本必须同场景配对**

| 类别 | 场景 | 为什么必须有 |
|---|---|---|
| 正样本 | 教室课间、走廊、楼梯口／厕所门口（隐蔽场所）、操场、食堂 | 隐蔽场所是专项行动明确要求覆盖的重点，也是围殴高发地 |
| 正样本 | 单人被多人围困（≥3 人）、对等互殴、推搡、踢打、财物勒索、辱骂施压 | 覆盖欺凌判别的各个分支 |
| **难负样本** | 课间嬉闹、追逐打闹、排队、并肩同行、拍肩／拥抱、体育活动、搬桌椅、蹲下捡东西 | **指标由分母决定**。没有难负样本，误报率永远是 0，这个 0 毫无意义 |
| 空场景 | 无人教室／走廊 | 单独测"静止画面下的误报"与运动门控收益 |

**二、拍多久**

- 正样本：每类 **≥30 段**，单段 10~30 秒（一次事件的自然长度）→ 约 30 段 × 6 类 ≈ 90 分钟；
- 难负样本：每类 **≥30 段**，单段 15~30 秒 → 约 30 段 × 8 类 ≈ 100 分钟；
- 空场景：每场景 5 分钟 → 共 25 分钟；
- **合计约 3.5 小时素材**。这个体量足以给出可答辩的 P/R/F1 与阈值敏感性曲线，
  又不需要等到"先建一个大库"才能开始。

**三、怎么标**

1. **段级标签为主**：`{起始时间, 结束时间, 事件类型, 参与人数, 强度}`。判定指标按**事件段**统计，
   不按帧统计 —— 帧级指标会被"同一事件连续上报多少帧"稀释，读不出实际可用性；
2. **双人独立标注 + 分歧仲裁**：两人分别标，分歧段由第三人仲裁，报告标注一致性
   （Cohen's κ 或 Krippendorff's α **≥ 0.8** 才认为标签可用）；
3. **工具**：CVAT 或 Label Studio（均开源、可本地部署，符合"数据不出校"的合规要求）；
4. **采样策略必须与线上一致**：评测脚本必须复用 `video_pipeline` 的运动自适应采样，
   否则测的是另一套东西 —— 早期用固定 0.33s 步长时就曾把"采样跳过了 0.35 秒的推搡"
   误判成"算法测不出来"；
5. **合规前置**：涉及真实学生的素材**必须先取得监护人同意**，或用同学龄志愿者扮演；
   素材仅在校内设备留存、不公开传播；标注人员同样签署保密承诺。

**四、拿到数据后要算的指标**

| 指标 | 口径 | 说明 |
|---|---|---|
| 事件级 P / R / F1 | 按事件段，IoU ≥ 0.5 视为命中 | 主指标 |
| **误报率** | **次 / 小时**（而非帧级 FPR） | 工程上更被校方接受，也更能反映值班老师的实际负担 |
| 首次报警时延 | 事件开始 → 系统首次报警的秒数 | 体现"早发现"的实际价值 |
| 阈值敏感性 | 关键阈值 ±20% 时的 P/R 变化 | 证明结论不依赖于某组"调出来的"阈值 |
| 消融对比 | 4.3 节的 A/B/C/D 四组 | 证明每个模块都有独立贡献 |

**五、优先级建议**：先补"难负样本 + 空场景"，再补正样本。原因是当前系统的
**主要风险是误报而不是漏报**（第 4.4 节局限 2 已实测到聚集误报），
而误报只能靠负样本暴露出来。

## 五、伦理与合规专章

| 议题 | 我们的做法 |
|---|---|
| 数据最小化 | 隐私遮蔽区域不落盘；**未取得同意者不入人脸底库**；人脸特征与注册照仅存本机；留存 90 天后自动清理 |
| 告知与同意 | 系统内置《人脸信息处理告知同意书》模板与同意留痕台账（`consent_records`），建档时同步登记，撤回即刻删除特征 |
| 避免二次伤害 | 报警仅推送给值班教师，不公开、不点名；人工复核后才进入干预流程；未识别人员只显示行为线索，不猜测身份 |
| 误报处理 | 复核闭环量化误报率；阈值可调；宁可漏报不误伤（嬉闹抑制偏保守）；人脸识别采用"阈值 + top1/top2 间隔 + 轨迹级三票"三重闸门 |
| 算法透明 | 判定依据实时可视化（`explain` 面板），依据可追问、可复核；人脸识别的相似度与候选也在界面可见 |
| 责任边界 | 系统定位为**辅助预警工具**，最终判定与干预由教师完成 |
| 情绪识别 | **只做实时辅助线索，不落库、不写入学生档案、不参与任何评价**；界面固定标注"仅供参考，非心理诊断" |

### 5.1 人脸识别合规：条款 → 实现对照

《人脸识别技术应用安全管理办法》（网信办/公安部令第19号，2025-06-01 施行）是本项目新增
人脸识别能力时必须逐条落实的规范性文件。我们把每一条都落到了具体实现上：

| 条款 | 要求 | 本系统的实现 |
|---|---|---|
| 第四条 | 特定目的、充分必要、影响最小 | 仅用于校园欺凌事件的身份归属与通知；不做考勤、不做消费、不做行为画像 |
| 第五条 | 以显著方式告知处理者、目的、方式、期限、权利 | `/api/compliance/notice` 提供《人脸信息处理告知同意书》完整模板，可直接打印归档 |
| 第六条 | 取得**单独同意**，并提供便捷的撤回方式 | 建档接口强制携带 `consent_subject`；人员档案页一键「撤回」，**撤回即删除全部特征与照片**（不是只改状态位） |
| 第七条 | 不满 14 周岁须取得**监护人**同意，并制定专门处理规则 | 同意主体分「本人 / 监护人」；学生档案库内含监护人姓名、电话、关系字段；同意书模板含监护人签署栏 |
| 第八条 | 人脸信息**应存储于设备内、不得通过互联网对外传输**；保存期限最短 | 特征与照片仅落本机 `backend/data/faces` 与 SQLite；系统无任何对外上传人脸的接口；撤回即删除 |
| 第九条 | 事前开展**个人信息保护影响评估（PIA）**，报告与记录至少保存 3 年 | `pia_records` 台账 + `/api/compliance/pia` 登记接口 + 到期自动提醒复评；`audit_logs` 记录处理活动 |
| 第十条 | **不得作为唯一验证方式** | 人员档案支持手工录入与 CSV 批量导入；未建档人员同样参与行为检测与报警，不因未录人脸而失去保护 |
| 第十三条 | 公共场所安装需为维护公共安全所必需，并设置**显著提示标识** | 合规自查看板中设为待办检查项，提醒校方张贴并拍照存档 |

**合规自查看板**（`/api/compliance/overview`）把上述要求折算成可读数字：
同意覆盖率、已授权/已撤回人数、人脸模板数、PIA 有效期、以及 8 项检查清单的完成状态。
这一设计的目的很直接 —— 让学校在**任何时刻**都能回答"我们做得对不对"，
而不是等到被问询时才去翻制度文件。

**引擎选型也包含合规考量**：本项目采用 OpenCV **SFace**（Apache 2.0，可商用），
而非精度略高的 InsightFace buffalo 系列 —— 后者代码虽为 MIT，
但其预训练权重官方明确声明**仅限非商业学术研究**，若学校后续要实际部署会构成授权风险。

### 5.2 情绪识别的伦理边界

面部表情 ≠ 真实情绪，更不等于心理状态。因此本系统的情绪识别被刻意限制在一个很窄的用途内：

- **只用于实时提示**：让值班老师更快注意到"这个孩子此刻看起来很难受"，作为人工观察的补充；
- **不落库**：情绪概率只存在于内存，随轨迹消失而消失，数据库中没有情绪字段；
- **不进档案**：学生详情页不展示情绪历史，也不提供任何情绪统计报表；
- **不参与评价**：不与考勤、操行、成绩发生任何关联；
- **界面标注**：所有情绪展示处固定悬浮说明"基于面部表情的实时估计，仅供参考，非心理诊断"。

在答辩中，这一节的价值不在于"我们做了情绪识别"，而在于**我们能说清哪些事我们拒绝做**。

### 5.3 政策对齐话术（可直接用于申报书）

> 本系统响应教育部「校园暴力与学生欺凌防范治理专项行动」中关于隐蔽场所视频监控全覆盖
> 的要求，并通过数据最小化设计回应该行动对隐私保护的关切；同时对应《治安管理处罚法》
> 修订后学校「留证 + 报告」的法定义务，以自动取证降低学校的合规成本。
>
> 在引入人脸识别能力时，本系统严格对齐《人脸识别技术应用安全管理办法》：取得单独同意
> （不满 14 周岁取得监护人同意）、人脸信息仅存于校内设备且不通过互联网传输、提供便捷的
> 撤回方式且撤回即删除生物特征、事前列入个人信息保护影响评估台账、并保留人脸识别之外
> 的替代方案，不将其作为唯一验证方式。

### 答题原则

- **不回避短板**：主动承认局限（如「合成场景只验证逻辑，真实指标待试点」），比被问出来更可信；
- **用数字说话**：凡是能给出数字的地方都给数字，不能给的要说明为什么（如「样本不足，判定趋势需要 ≥3 条」）；
- **区分「已验证」与「已规划」**：不要把规划中的功能说成已实现；
- **引用要准确**：论文、数据集、赛事规则必须能给出出处。
